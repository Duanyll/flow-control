# Writing docs

`docs/` covers what a reader cannot get by reading the code top-down: designs spread across threads, generators, ranks or several modules, the intent behind them, and the boundaries code must respect. What the code states plainly stays out; an agent can read the code at any time.

## What belongs here

- **Chapters** on the library, one per subsystem (data, sampler, models and variants, rollout and rewards, training, ...).
- **Guides** to external technology as this repo uses it (FSDP2 and DCP). Link the official docs for the rest, and re-check against the current upstream version when editing one.
- **Reading** material independent of the library (paper lists, blog notes), under `reading/`.

Never here: task reports, implementation checklists, status or progress notes, validation and benchmark records, investigation logs, model-integration diaries. They belong in `draft/` or `local/<slug>/`, or in the commit message. If such work found something that constrains future code, add it to the relevant chapter as one line of why, or as a comment at the code site.

## Layout

`docs/README.md` is the table of contents. Each chapter is a directory named after its subsystem; split a chapter into several files only when it covers separable concerns. Add every new file to the index. Link to another chapter instead of repeating it.

## A chapter

In this order:

1. **Purpose**: one or two sentences on what the subsystem is for and the concepts it introduces.
2. **Config examples**: what doing each task looks like at the config level.
3. **Diagram**, when the control flow is not a straight line.
4. **Python spec**: the interfaces, how to use them and how to implement one.
5. **Extension points and core contracts.**

### Config examples

- jsonc, one block per task, titled by the task ("SDEdit", "Autoguidance").
- Only the fields the task needs. Show a default as a commented-out line (`// "sigma_end": 0.0`); use a trailing `//` for shorthands and non-obvious values.
- Field names and nesting match the current pydantic models (`schema/*.schema.json`, generated by `uv run flow-control schema`).

### Python spec

- Signatures, fields, and only the body lines that carry the design. Drop logging, validation and error handling unless they are the point.
- Show a caller using the interface, and a minimal implementation of each extension point.
- Explain with trailing `#` comments on the line, not paragraphs between blocks.
- Use the names in the code. A sketch may simplify but must not contradict the code.

### Diagrams

Use mermaid for anything whose flow is not top-down: concurrency (threads, async, generators), collectives across ranks, multi-stage pipelines, lifecycles. `flowchart` for how data moves, `sequenceDiagram` for who waits on whom. Label nodes with real symbol names; one diagram per question, small enough to read at a glance.

### Math

Formulas live in `math/`, in the notation of `math/notation.md`; add a symbol to its table before using it. Other chapters link the formula instead of restating it. Write LaTeX for GitHub (`$...$` inline, `$$...$$` display), match the code exactly (clamps, epsilons, which σ), and name the code symbol that computes each formula.

### Extension points and core contracts

This section tells an agent where it may build freely and where it must stop and ask.

- **Extension points**: the registry and base class, what a new member implements, what it may read and write, and where it lives (`flow_control/contrib/`, or `local/` loaded through `imports`). An experiment that fits an extension point needs no design discussion.
- **Core contracts**: the abstractions many modules depend on (row keys, the `Calls` protocol, the executor's collective round, ...). Changing one is a discussion with the user before any code; the chapter changes in the same commit as the code.

## Prose

- Write why (design intent) and how (boundaries to keep). Do not narrate what the code does; name the symbol and let the reader open it.
- State things directly. Write a limitation once, where a reader would hit it, as a fact ("`cfg_pp` raises outside an Euler step"). Do not attach a hedge to every claim ("..., but this does not guarantee ...", "this only shows ..., not enough to prove ...").
- Describe the current code only: no history, dates, "now" / "previously" / "no longer", removed APIs, migration notes or before/after. A refactor may start as a spec in this format; its removed and migration lists go in the commit message.
- No introduction or summary paragraphs, no filler. Bold only where a term is defined.
- Be concise. Refer to code by file path and symbol name, never by line number.
